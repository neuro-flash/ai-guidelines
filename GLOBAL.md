# Language-specific rules

Depending on the language of the files you modify, also apply (downloaded as described in [SETUP.md](SETUP.md)):

- Go: `~/.ai-guidelines/go.md`
- TypeScript: `~/.ai-guidelines/typescript.md`

# Code comments

- Use as few comments as possible. Only add one if it contains really important information not obvious from the code.
- Keep comments as short as possible. After writing, reread them and condense further.

# Commit messages & PR descriptions

- Be as short as possible. No verbose language. After writing, recheck and remove anything that can be removed.
- Never describe what was done (visible in the code). Only the why and the impact: which bug is fixed or which feature is added.
- Only mention things affecting the outside of the service (API endpoints, events, etc.) or significant logic changes. Never list changed classes/files/functions.
- Example: "Fix credit note refunds always failing."

# Branches

- Prefix branch names with `feature/` or `bugfix/`.
- If the change relates to a ClickUp ticket, include the ticket id in the branch name and commit message.

# Pull requests

- "Assign a PR to someone" means request them as reviewer. Never use the PR assignee functionality.
- After committing and pushing, check for an open PR on the branch and update its description if needed.
- One feature per PR. Larger cleanups, extra functionality or mass reformatting go into a separate branch/PR.

# API design

- Paths start with `/v1`, use plural kebab-case resource names: `GET/POST /customers`, `GET/PUT/PATCH/DELETE /customers/{id}`.
- Every resource has one UUID id, generated by the backend, used in paths and as the DB primary key.
- Parent resources belong in the path, not the payload, and consistently across all endpoints of a resource (`POST /projects/{projectId}/conversations`).
- Create resources with `POST` on the plural collection path (no id in the path).
- Filter via camelCase query params matching JSON fields (`?firstName=Karla`).
- Error translation keys are always camelCase (`stripeCouponNotFound`, not `STRIPE_COUPON_NOT_FOUND`).
- Responses must not differ based on feature flags.
- Related entities go in an `_embedded` field, only if the service already has them in its own DB.
- Serve files via signed bucket URLs, never proxy them through the service.
- New entities/domains and their endpoints, paths and payloads must be aligned with the dev team before implementation. Update the API docs afterwards.

# Services

- Services must be stateless and horizontally scalable: no request-spanning state in memory or on local disk. Use DB, buckets, redis etc.
- Keep startup fast. Closely linked features stay in one service, independent ones may be split.
- Every service must be runnable and testable locally.
- Hide unreleased features behind a feature/system flag so main stays deployable.

# Logging

- Log `context.userId` and `context.requestId`. Generate the request id if missing, propagate it via the `X-REQUEST-ID` header and return it in the response.
- Avoid personal data (email, name) in logs.

# Prompts

- Define required LLM output formats as dedicated Langfuse prompts in the `output-formats` folder, with the JSON schema in the config.
- Never introduce breaking changes (new required field, removed required field, rename, type change). With rolling deployments, old and new code run in parallel: add the new field, support both, remove the old one only in a later release.

# Secrets & infrastructure

- Never commit or share secrets in plaintext. Use Google Cloud Secrets or Vaultwarden.
- Never modify GCP infrastructure outside the playground directly. Use terraform.
